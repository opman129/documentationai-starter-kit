## Best Practices

<Tabs>
  <Tab title="Keep It Concise" icon="file-text">
  
  Write short bullets that explain the user impact. Avoid repeating the same point across multiple sections.
  
  </Tab>
  <Tab title="Use Clear Labels" icon="tag">
  
  Use consistent release labels such as `v1.4.0` and keep dates in `YYYY-MM-DD` format.
  
  </Tab>
  <Tab title="Review Before Publishing" icon="shield">
  
  Check for missing dates, accidental duplicates, and changes that may require migration notes.
  
  </Tab>
</Tabs>

## Optional Notes

<Callout kind="info">
  If your release includes a migration step, call it out clearly and place it near the top of the entry so readers do not miss it.
</Callout>

<Expandable title="What should you include in each release?" default-open="false">

Include the changes that affect users the most. A good entry usually contains a short summary, a few bullets for the main updates, and a note about any breaking change.

You can also add references to related pages, testing notes, or rollout details if your team needs that extra context.

</Expandable>

## Version History Guidance

Keep the latest version first, then work backward through earlier releases. That order helps readers find the newest changes without scanning the whole page.

When you maintain multiple versions, use one update block per release and keep the structure consistent. That makes the page easier to read and easier to maintain over time.
